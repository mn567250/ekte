# Accessibility of web UI v2

Web UI v2 (`/v2/…`) targets **BITV 2.0**, which requires **EN 301 549**, whose
web chapter 9 is **WCAG 2.1 level A + AA**. BITV-Test step numbers are the
EN 301 549 clause numbers (WCAG 1.4.3 → 9.1.4.3).

`tests/a11y/` checks as much of this as a machine can, in a real browser
(Playwright + Chromium, rules by [axe-core](https://github.com/dequelabs/axe-core)
4.13, vendored in `tests/a11y/vendor/`). Every page (`/v2/`, `/v2/history`,
`/v2/watches`, `/v2/tools`, `/v2/kb`, `/v2/analytics`, `/v2/accessibility`) is checked **in every UI language**
(`zing/i18n/locales/*.json`: de, en, es, fr, it, pt, zh), in light and dark
theme, as loaded and with every disclosure opened (rendered report, advanced
options, monitor details) and every tab panel shown.

```bash
pip install -e '.[web,a11y]'
playwright install chromium            # or ZING_A11Y_CHROMIUM=/path/to/chrome
pytest -m a11y -n auto                 # pytest-xdist, in the dev extra
```

Findings are also written to `a11y-report.json` (`ZING_A11Y_REPORT` moves it).
`ZING_A11Y_SHARD=k/n` runs only the k-th of n equal parts of the suite (the
slowest tests are spread evenly). `ZING_A11Y_PAGES=history,kb` runs only the
tests of those pages, plus the checks that compare every page (consistent
navigation and identification, page titles, reachability); the two combine.

In CI an `accessibility scope` job decides what to test
(`python -m tests.a11y.affected`, mapping in `tests/a11y/pages.py`, see
[tests/a11y/README.md](../tests/a11y/README.md)): every page on pushes (to `main`
and the integration branches), the nightly run and manual runs, in four
`accessibility k/4 (informational)` jobs; on pull requests only the pages
the change can affect, in one to four jobs, and nothing for changes
outside the web UI. A file shared by every page, or a web UI file the mapping
does not know, runs everything. The jobs run without failing the pipeline and
upload those files; they become a required check once the suite is green.

## Coverage by BITV / EN 301 549 test step

The catalogue `zing/web/static/v2/bitv-catalogue.json` is the single source of
truth for the 50 test steps (WCAG 2.1 A + AA): number, level, title, how far
the tests decide the step and how. `tests/a11y/bitv_map.py`, the conformance
report and the report page read it. Every a11y test names the steps it decides
with `@pytest.mark.bitv("9.1.4.3", …)`; the table below is generated from the
catalogue and those markers (`python -m tests.a11y.conformance --docs`).

**auto**: decided by the tests. **partial**: the tests catch the common failures,
and a person still judges the rest. **manual**: needs a person. **n/a**: the UI
has no such content (no audio or video).

## Conformance report (`/v2/accessibility`)

The page **Accessibility** (the accessibility icon next to the language switch
in the header of every v2 page) shows, per test step, how it is tested and the
latest result, plus a short accessibility statement (conformance status, known limitations, how it was assessed,
feedback). It renders `zing/web/static/v2/bitv-report.json`, built from a real
run of the suite:

```bash
ZING_A11Y_RESULTS=a11y-results.json pytest tests/a11y -m a11y -n auto
python -m tests.a11y.conformance --results a11y-results.json [--llm a11y-llm-review.json | --no-llm]
```

`ZING_A11Y_RESULTS` makes the plugin `tests/a11y/results.py` write, for every
step, the tests that ran with their outcome and failure summary. Tests added
later need only the `bitv` marker. axe-core tests cover many steps at once, so
their outcome is split per rule: a step fails only when an axe rule tagged with
its criterion (`wcag143` → 9.1.4.3) reports a violation, and a step whose axe
rules were all inapplicable counts as not tested.

Per step the report says **pass** (auto step, every test passed), **fail**
(a test failed), **manual review pending** (partial or manual step: the
automated part passed, a person still has to judge the rest), **not tested**
(no test ran yet) or **n/a**. The headline stays "partially conformant" until
every applicable step passes *and* a manual review is recorded.

**LLM review of the texts.** When `a11y-llm-review.json` (written by
`python -m tests.a11y.llm_review`, see
[tests/a11y/README.md](../tests/a11y/README.md)) is in the working directory or
given with `--llm`, a completed review counts as the manual part of the steps
it covers (9.1.1.1, 9.1.3.3, 9.2.4.4, 9.2.4.6, 9.3.3.2, 9.3.3.3): a step whose
automated part passed **passes** when the review found nothing and **fails**
when it found an issue, with the findings shown under the step. The report
then records a manual review, and the page names the model that made it. A
failing automated part still fails the step, an untested one stays not tested,
and a review that was skipped, failed, a dry run or did not cover every tested
page and language changes nothing. Without the file (or with `--no-llm`) the
report is built from the tests alone. Hand-written notes in the older
`{"steps": {...}}` form are shown with their step without changing its status.

The page renders `bitv-report.json` only, so a new review shows up once it has
been applied to that file: `python -m tests.a11y.llm_review --update-report`
reviews and updates the report in one command, and
`python -m tests.a11y.conformance --update zing/web/static/v2/bitv-report.json
--llm a11y-llm-review.json` applies an existing review file without running
the suite or the review again. Each step keeps its status from the tests
alone (`status_tests`), so a newer review replaces the older one.

CI runs the suite with `ZING_A11Y_RESULTS`, one results file per shard. The
`accessibility report` job merges them (`--results` takes several files),
generates the report even when tests fail and uploads `bitv-report.json` with
the other findings. When the `ANTHROPIC_API_KEY` secret is set, it runs the LLM
review first and builds the report with it. It does so for full runs only: a run of some pages would
report the steps of the others as not tested, so a partial run uploads its
findings and names the pages it tested in the job summary. The copy
committed in the repository is regenerated with the commands above.

## Manual review still needed

Before claiming BITV conformance, have a person check the **manual** rows and
the human part of the **partial** rows, ideally with a screen reader (NVDA +
Firefox, VoiceOver + Safari):

- meaningful alt texts and labels
- logical reading and focus order
- understandable error messages
- announcements of status changes (an audit starting, finishing or failing)
- the chart alternatives (data tables and summaries)
